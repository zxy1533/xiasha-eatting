# 需求与约束清单｜下沙「今天吃什么」小程序

> 阶段：Phase 0。张鑫宇，中国计量大学大一。核心两块：避雷周边难吃饭店，以及不知道吃什么时让问答机器人替他拍板。
> 这份清单锁边界和验收，不列行业通用功能。数字标了假设的，锁模型/锁规模后要回来改。

## 0. 三条已经拍板，不在本清单里重新讨论

1. 问答机器人全接大模型。不做本地规则排序，不做规则+模型的混合兜底。
2. 发布范围是全校同学，不是体验版白名单小范围内测。
3. 种子数据用张鑫宇 @ 的那份微信共享表格清洗后得到，不另造数据。

这三条带来的成本冲突不靠推翻决策解决。护栏（限次、月度封顶、缓存、脱敏、Key 放云函数）作为硬约束写进方案，见 §5 和 §6。

## 1. 谁在用，什么时候用

主要用户就是张鑫宇这类在校生：宿舍点外卖、食堂吃腻了、预算有限、对某几家店有明确雷区。技术水平是会用微信，不会配任何东西。

按一天里的时间排，场景是这样的：

- **午餐（11:00–13:00）**。课间刷一下，要在 1 分钟内定下来。最怕的是点了一家没吃过的，难吃还贵。这里的动作是打开就问"今天吃什么"，或者先查一眼某家店雷不雷。
- **晚餐（17:00–19:30）**。选择困难最集中的时段。会问"想吃辣的/便宜的/能堂食的，有啥推荐"。这里真正要解决的不是"给个榜单"，是"替我定一个，别让我继续挑"。
- **夜宵（21:30 以后）**。量小、别太撑、配送快。种子表格里有"外卖省钱""少送餐品"两张表正好对上这个场景。
- **团建/聚餐**。少数场景，但要查"这几个人一起吃什么不踩雷"，偏向堂食。"好吃的堂食店"表覆盖这一部分。
- **纯选择困难**。不绑定饭点，就是打开问一句。这个场景决定了机器人必须是自然语言入口，不能只做几个筛选按钮。

次要用户是帮他一起填表格的同学。MVP 里他们不进小程序，继续在微信表格里接力填；小程序只消费清洗后的数据，不做投稿入口（见 §3）。

## 2. MVP 做这 7 件

每件写清楚它解决哪个决策痛点、最小实现做到什么程度。"最小实现成本"是这一件单独做出来要花的力气，不是整项目工期。

| # | 功能 | 解决的决策痛点 | 最小实现成本 | 可砍？ |
|---|------|----------------|--------------|--------|
| F1 | 种子表清洗与入库（离线，一次性） | 表格是接力填的，脏数据直接进模型=编造+翻车，这是所有功能的前置 | 脚本去重+店名归一化+人工抽检一轮；产出一张"店名/避雷/证据原话/标签"的干净表 | 不可砍 |
| F2 | 避雷查询：按店名或商圈查"这家雷不雷" | 点外卖前那 10 秒，想知道有没有人踩过 | 在干净表里做店名匹配，返回"雷/不雷/有争议"+1–2 条脱敏学生原话。走本地数据，不调大模型 | 不可砍 |
| F3 | 问答机器人（全接大模型） | "今天吃什么"的选择困难，要的是有人替我定 | 云函数转调大模型，注入脱敏后的种子片段，返回 1 家带一句理由。流式输出 | 不可砍（用户已定） |
| F4 | 理由与出处：推荐/避雷都能点开看学生原话 | "凭什么信你"，没有证据的推荐等于没说 | 返回命中的评价原文 1–2 条，已脱敏；前端一个可展开区 | 可砍（但会显著削弱信任） |
| F5 | 换一批／再来一个 | "这家不想吃"，要能再给一个且别重复 | 前端带排除项再调一次大模型；排除列表随会话传 | 可砍 |
| F6 | 我的避雷/想吃清单 | 记不住上次踩雷的是哪家 | 小程序本地 storage 存店名列表，不联网、不建账号 | 可砍 |
| F7 | 用量与降级护栏 | 开放全校后调用量失控，账单跟着失控 | 每人每日限次、月度封顶、缓存、脱敏、Key 只在云函数；到顶即停，不切本地规则 | 不可砍（用户决策的强制代价） |

F1 要处理的具体脏数据，来自我实际打开表格看到的：

- 同一家店写好几种名字，三张近义的"好吃的"表（好吃的 / 好吃的(2) / 好吃的 (2)）和两张"好难吃"表要合并。
- 大量"点了"刷屏，没实质内容，要当噪声剔掉；真正的评价是夹在里面的短句。
- 同一家店正面负面都出现。纸包鸡在"好吃的"表里有人说 yyds，也有人说"表里有人说不好吃捏"；稻川岛滑蛋饭一边"真的很好吃"一边"超难吃，吃过一次就不愿再试"。这类店标"有争议"，不能只取一边。
- 表里混着交友、情绪、辱骂、昵称，比如蹲某位同学的搭话、跟爸妈的私人倾诉。这些跟吃无关，且是别人的个人信息，清洗时必须过滤。
- 没有结构化评分字段，只有文本。所以"这家几星"这类需求 MVP 不做，能给出的只有"褒/贬/争议+原话"。

数据缺口（表格里查不到，别编）：人均价格只有零星提及，没有稳定字段；距离、营业时间、堂食/外卖属性都不全。涉及这些的筛选先不做。

## 3. 明确不做的 3 项

1. **不做用户公开点评/发帖/评论区**。开放全校后再放开 UGC，审核和责任都跟着来，表格数据也会被污染。MVP 只消费种子表，同学想补充就去原表格接龙。
2. **不做支付、下单、外卖履约**。没有资质也不是核心，这个小程序停在"帮你决定去哪吃"，不碰交易。
3. **不做本地规则排序或混合兜底**。这条直接来自用户决策：机器人全接大模型。预算到顶时是"停止调用并给静态提示"，不是切换回本地规则——前者是限流，后者才是被否掉的方案。

## 4. 验收标准（可测）

- AC-01 避雷查询：输入库内完整店名，1.5s 内返回褒/贬/有争议判定和至少 1 条脱敏原话；查无此店时明确提示"表里没有这家"，不编造。
- AC-02 问答响应：自然语言提问，流式首字 < 3s，完整回答 P95 < 8s；返回恰好 1 家店和至少 1 句理由。
- AC-03 不编造：抽 50 条问答返回，里面出现的店名 100% 来自种子库；库外店名出现次数为 0。
- AC-04 脱敏：检查发给大模型的 payload，字段在约定白名单内，不含昵称、头像、学号、精确时间戳。
- AC-05 换一批：连点 3 次换一批，结果在种子库容量允许范围内不重复。
- AC-06 限次降级：单用户当日调用达上限后，抓包确认大模型请求数归零，前端返回静态提示。
- AC-07 预算封顶：月度累计达封顶值后全局停调用，但避雷查询（走本地数据）仍可用。
- AC-08 Key 安全：小程序前端构建产物里搜不到任何模型 API Key 字符串。
- AC-09 异常态：无网、大模型超时或返回空时，有明确提示，不白屏不崩溃。

P0 界面与文案约束：功能图标用统一 SVG 图标库，不用 emoji 当图标（具体库由架构师锁）；不出现紫到粉的渐变；文案不写"欢迎使用""Lorem ipsum"这类空话，直接说这家店能不能吃、为什么。

## 5. 成本：用户选择与护栏的正面冲突，怎么落

**冲突原样说清楚。** 提示词包第 41、69、101–104 行写的是：10–30 人小范围、体验版白名单、本地 rules.json 排序、大模型只做解释层、缓存限次封顶 Key 放云函数、缓存未命中率压到 10% 以下。用户拍板的是相反的三条：机器人全接大模型、开放全校、用真实表格。两件事正面撞上。

**处理方式：不推翻用户选择，把护栏焊成硬约束。** 护栏不改变"全接大模型"这个决策——机器人做的每一次判断仍然来自大模型；护栏只是限制谁能调、调多少次、花到多少停。"全接大模型"换成"本地规则兜底"才叫推翻，这里没有。到顶后的动作是停止调用并给静态提示，或者返回缓存里已有的大模型生成结果，两种都不引入本地规则。

**成本公式**（改写自提示词包第 101 行的解释层公式；本项目机器人每一轮对话都是一次调用）：

```
月成本 ≈ 日活人数 × 人均每日轮数 × (1 − 缓存命中率) × 单次成本 × 30
单次成本 = 输入token × 输入单价 + 输出token × 输出单价
```

**假设，都要待确认：** 输入 1500–4000 token（system 提示 + 注入的脱敏种子片段 + 用户问题），输出 150–400 token；单价按低单价国产模型按量计费估，输入 ¥0.001–0.004/千 token、输出 ¥0.002–0.008/千 token。单次成本区间约 **¥0.002–0.019**，中位按 ¥0.007 估。全校规模按 2 万人估，日活渗透 5%–15%。这些数字锁模型、锁规模后收敛。

| 场景 | 日活 | 人均轮数/日 | 缓存命中 | 月成本估算 |
|------|------|------------|----------|------------|
| 保守 | 1000 | 2 | 30% | ¥80–800 |
| 中性 | 2500 | 3 | 20% | ¥320–3500 |
| 激进 | 4500 | 5 | 10% | ¥1100–11700 |

**必须做进方案的护栏（逐条再确认一遍，别在实现时被省掉）：**

- F7-a 每人每日调用上限。建议先设 10 次/人/日，超限返回静态提示，不再发起请求。
- F7-b 月度总预算封顶。建议先设 ¥300/月试运行，到顶全局停调用，避雷查询不受影响。
- F7-c 缓存。相同/近似问题复用大模型已生成的结果；因为有"注入种子片段"这一步，缓存 key 要包含命中的店和上下文，别把不同问题的答案串了。
- F7-d 脱敏后再发送。传给大模型的字段走白名单，控制 ≤5 个，昵称/头像/精确时间一律不带。
- F7-e API Key 只在云函数，前端构建产物里不得出现。
- F7-f 并发和频率限制，防同一个人脚本刷。

## 6. 风险与待确认

**风险，按严重程度排：**

1. **成本失控（最大）**。开放全校 × 每次决策都调大模型，调用量跟传播走，不设上限就是开放式账单。缓解 fully 依赖 §5 的 F7-a 到 F7-f，尤其封顶和限次。
2. **数据脏导致翻车**。表格里褒贬混写、店名多写法、无关个人信息一堆。清洗做不干净，机器人会拿"点了"当好评、拿交友帖当评价。F1 是前置条件，不是可选项。
3. **大模型编造**。会说出库里不存在的店或评价。约束写进 system 提示"只能用给定数据回答"，返回后在云函数做店名白名单校验（AC-03）。
4. **合规与授权**。开放全校可能触及面向不特定公众，微信类目和资质待确认；评价涉及他人，脱敏是底线。
5. **延迟**。全大模型比本地规则慢，饭点等 8 秒会流失。流式首字和缓存缓解，不承诺 3 秒出完整答案。

**待确认项，每条带我的推荐项：**

| 问题 | 为什么必须确认 | 推荐项 |
|------|----------------|--------|
| 用哪个模型、商务单价多少 | 成本公式里最敏感的变量，没它全是区间 | 先用低单价国产模型按量计费，架构师锁型号后回填 |
| 全校实际人数和预估日活 | 决定成本量级，现在只按 2 万人假设 | 先按 2 万学生、日活 1000 做保守预算 |
| 微信发布类目与资质 | 开放全校是否算公开传播，直接影响能否上线 | 先体验版跑通，正式发布前补类目 |
| 表格里的学生评价能否用于公开小程序 | 授权没确认就上线有风险 | 默认脱敏后可用，但要张鑫宇明确点头 |
| 月度封顶和每人每日上限的具体数值 | 护栏数值决定体验和账单的平衡 | 先设 ¥300/月、10 次/人/日，跑一周再调 |
| 工期与人力 | 成本模型里工具类小程序 1–1.5 人月、AI 应用 2–3 人月；本项目是工具+LLM | 暂按 1.5–2 人月，架构师拆完页面再定 |
